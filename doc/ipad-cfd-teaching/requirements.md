| 决策点 | 裁决 | 理由 / 后果 |
|---|---|---|
| **源码入门（FR4）是否核心差异化** | **保留为核心** | 接受其连带成本（源码面板、函数↔源码映射、公式渲染、点代码联动探针整套子系统）+ GPL 合规债（C3）。这是与普通 CFD 演示 App 的本质区别，砍掉即沦为流场玩具。FR4 还是 FR5、FR7 的依赖锚点（无源码切分则无可探查/可问对象）。 |
| **是否新增"保存/分享"** | **接受为 FR6，但划出 MVP** | 选定形态 = 本地保存 + 分享，**不进首版**（发布后里程碑）。现阶段只澄清"怎么做"（§7），不实现。 |
| **学习路径：自由探索 vs 引导式关卡** | **自由探索 + 最轻量首次引导** | 关卡系统是独立大功能；NFR2"防挫败"用"预置必出结果 + onboarding 气泡"即可满足。 |
| **"课堂场景"是否设计目标** | **明确不做**（2026-06-11 修订） | 唯一目标用户 = 单个自学者。课堂/多人协作/教师视角列入"不做"清单（§6）并标注决策以备追溯。与原"降级"的工程效果相同（都不建课堂功能），区别仅在于写入明确排除项而非留作"潜在场景"。 |
| **是否新增 AI 源码问答（FR7）** | **接受为候选，发布后；离线取舍待定** | 选中代码符号 → 把该片段作为上下文注入 AI 对话，免手敲代码。是 FR4 的自然延伸（复用其函数↔源码切分）。**开放问题：与 NFR5 离线冲突**，建议"核心离线 + AI 可选在线"（见 §7）。 |

## 1. 愿景

iPad 上的**教学型 CFD App**，定位是 OpenFOAM 的「引桥课」：让初学者**零环境成本**在 iPad 上走通一次「从输入到流场结果」的完整闭环，并能**对照真实 OpenFOAM 源码**建立心智模型，然后再去面对真正的 OpenFOAM。

两条边界声明（防愿景漂移）：

- **不替代 OpenFOAM**，只解决"上手第一公里"。
- **核心差异化 = 源码入门**（教人看懂 OpenFOAM 的 C++）——这是与市面其他 CFD 演示 App 的本质区别（2026-06-10 确认保留）。

## 2. 目标用户

**主体（唯一目标用户）：单个 CFD / OpenFOAM 初学者**（自学者、学生）。画像：被 OpenFOAM 的环境配置（WSL/虚拟机/编译）和概念门槛劝退过，但有 iPad，想低成本入门。

**课堂 / 多人场景：明确不做**（2026-06-11 修订，见 §6 不做清单）。不引入教师视角、全班进度同步、布置/批改等需求。

## 3. 功能需求（FR）

> 追溯纪律：每条 FR 配一条**验收方式**（"怎么算你完成了"）。`范围`列标明是否进 MVP。

| 编号 | 需求 | 内容 | 验收方式 | 范围 |
|---|---|---|---|---|
| **FR1** | 运行 | 在 iPad 端上求解一个 CFD 算例并得到流场结果（首案例 = 2D 顶盖驱动方腔） | 对 cavity 跑到 `endTime`，得到流场；涡心位置、残差收敛趋势与真实 icoFoam 一致 | ✅ MVP |
| **FR2** | 编辑 | 用图形/表单方式编辑算例输入（边界条件、参数），同时可见等价的 OpenFOAM 字典文本 | 改一个边界条件/参数 → 表单与 dict 文本双向同步 → 重算生效 | ✅ MVP |
| **FR3** | 可视化 | 速度矢量/流线、压力云图、残差/收敛曲线、流场随时间演化 | 四类视图随时间步刷新且数值正确 | ✅ MVP |
| **FR4** | 源码入门 | 点 UI 上的概念/函数 → 看到对应的真实 OpenFOAM C++ 源码 + 解释 + 数学公式 | 点 `fvm.laplacian` 等 → 显示真实 `icoFoam.C` 对应行 + 公式 + 解释 | ✅ MVP |
| **FR5** | 交互式理解 | 单步/播放求解过程；点某个网格单元，查看它的数值和离散细节 | 能单步/播放 PISO；点某 cell 显示其 U/p 值与离散贡献（矩阵系数） | ✅ MVP |
| **FR6** | 保存/分享 | 保存改过的算例 + 结果快照到本地；可分享（导出图片/算例） | （随该里程碑细化；做法概述见 §7） | ⏳ 发布后 |
| **FR7** | AI 源码问答 | 选中（点击/长按）源码中的函数/类 → 该片段自动作为上下文注入 AI 对话框，用户免手敲代码即可追问 | （随该里程碑细化；做法与开放问题见 §7） | ⏳ 发布后（候选） |

## 4. 非功能需求（NFR）

> 决定架构的往往是这些条目（详见"需求→架构推导"一课）。

| 编号 | 需求 | 内容 | 验收方式 |
|---|---|---|---|
| **NFR1** | 零环境成本 | App Store 一键安装，无任何配置 | 安装后无需任何额外步骤即可运行首个案例 |
| **NFR2** | 防挫败 | 预置稳定参数，保证新手必出结果，先给成就感 | 预置参数下 100% 出结果、零崩溃；危险参数被锁在安全范围（见 C4） |
| **NFR3** | 触屏友好 | 无键盘也能完成全部输入（故编辑须图形化，FR2 的由来） | 全部输入可仅用触屏（表单/滑杆/选择器）完成，无需物理键盘 |
| **NFR4** | 交互性能 | 求解和渲染流畅到支撑"实时观看、随时单步"的教学体验 | 教学网格（20×20）下求解+渲染流畅；单步响应无可感卡顿、可连续播放 |
| **NFR5** | 离线可用 | 教学内容（源码、公式、解释）内嵌，无网也能用 _（FR7 AI 问答为可选在线增强，不破坏本条对核心内容的约束）_ | 飞行模式下：求解、源码、公式、解释全部可用 |

## 5. 约束（Constraints）

> 不是我们选的，是世界强加的（区别于需求）。

| 编号 | 约束 | 后果 |
|---|---|---|
| **C1** | App Store 规则 2.5.2：iOS 上不能编译用户现写的代码 | 求解器必须**预编译内置**；用户只能编辑**数据**（参数/边界），不能写代码 |
| **C2** | OpenFOAM 本体依赖 MPI/wmake/动态库机制 | 不现实整搬，引擎须**重新实现** |
| **C3** | OpenFOAM 是 GPL v3，与 App Store 分发条款冲突 | 内嵌其源码片段有法律风险（原型期内嵌、上架前改造，属架构阶段决策）；FR7 把源码发给第三方 AI 是又一接触点 |
| **C4** | CFD 数值方法本身会发散 | 新手乱改参数必炸 → 必须**锁定安全参数范围**（支撑 NFR2） |

## 6. 范围（MVP）

**做：**
- 一个案例（**icoFoam 求解器 + 2D 顶盖驱动方腔 cavity**）做到极致。
- 4 种边界条件：`fixedValue` / `noSlip` / `zeroGradient` / `empty`。
- 2D 均匀方形网格。
- **最轻量首次引导**（onboarding 气泡，满足 NFR2，非关卡系统）。

**不做（第一版明确排除）：**
- 3D、湍流、复杂网格生成、多求解器、用户自定义案例。
- **引导式教程关卡系统**（2026-06-10 裁决：走自由探索）。
- **课堂 / 多人协作 / 教师视角**（2026-06-11 裁决：唯一目标用户 = 单个自学者）。
- **FR6 保存/分享**（已记录为需求，延后到发布后里程碑）。
- **FR7 AI 源码问答**（已记录为候选需求，延后到发布后）。

**演进策略：** 架构上要求"**加新案例 = 加数据，不改框架**"；发布后按"加案例"迭代。

## 7. 延后项的做法概述（仅在"需求高度"上澄清，不下沉实现）

### FR6 保存 / 分享 —— 怎么做（概念层）

- **保存**：把当前算例的输入（边界条件/参数等结构化数据）+ 一份结果快照（某时刻流场 + 残差曲线）持久化到设备本地沙盒，下次可重新载入回看。本质是把已有的结构化案例数据 + 结果序列化成文件，**不依赖网络**（不破坏 NFR5）。
- **分享**：把保存的内容导出为可传递的产物，两种粒度——① **导出图片/动画**（结果截图，最简单、零隐私顾虑）；② **导出算例文件**（让对方载入复现，需稳定的导出格式 + 版本兼容）。再经系统分享面板（AirDrop / 邮件 / 消息）发出。
- **会牵出的次生需求**：导出格式定义与版本兼容；导入校验；隐私边界（教学 App 通常无敏感数据，低风险）；跨设备同步（超出"本地保存"范畴，属更大决策）。
- **为何正确延后**：不在"走通闭环 + 源码入门"核心价值链上，与引擎/可视化解耦，后期插入成本可控。

### FR7 AI 源码问答 —— 怎么做 + 开放问题（应需求方提议，仅需求高度澄清）

- **做法**：FR4 已经把源码按函数/类切分并建了"函数↔源码映射表"（每个符号挂着源码片段 + 解释 + 公式）。在此之上：用户点击/长按某个函数/类名 → 取它关联的源码片段（必要时附解释/公式）作为上下文，自动注入一个 AI 对话框 → 用户直接在引用后追问，无需手敲大段代码。**它是 FR4 的自然延伸**（从"读源码"升级到"就源码对话"），且复用 FR4 已有的切分基础设施，增量成本主要在 AI 后端一侧。
- **开放问题①（与 NFR5 离线冲突，必须正视）**：云端 AI 需联网，直接撞 NFR5。**建议解法：核心教学内容（源码+解释+公式，即 FR4 静态部分）保持离线可用；AI 问答作为"可选的在线增强"叠加其上——联网才用，不联网不影响核心。** 这样 NFR5 守住核心、AI 不破坏"零环境、随处可用"的卖点。备选：端上小模型（可离线，但 iPad 上质量/体积受限）。**此取舍留待该里程碑定夺。**
- **开放问题②（GPL，接 C3）**：把真实 OpenFOAM 源码作为上下文发给第三方 AI，是又一个 GPL 接触点，并入 C3 的上架前评估；若届时已按计划改用"自写等价讲解"作展示内容，则此问题被规避。
- **次生需求**：隐私披露（向第三方发送用户提问 + 代码，需 App Store 隐私声明）；AI 服务的账号/费用/限流；答案与"所展示源码语义"的一致性。
- **为何延后**：是 FR4 之上的增强而非核心闭环；MVP 仍按"先把 FR4 静态版做到极致"，AI 问答发布后迭代。

## 8. 追溯关系（可追溯纪律）

- **需求 → 验收**：见 §3 / §4 各条的"验收方式"列。
- **需求间派生/依赖**：FR2（图形化编辑）由 **NFR3 ∧ C1** 派生；NFR2 由 **C4** 支撑；FR5、FR7 依赖 **FR4**（无源码切分则无可探查/可问对象）。
- **需求间冲突**：FR7 与 **NFR5** 冲突，按"核心离线 + AI 可选在线"解（§7 开放问题①）。
- **需求 → 架构**（下一步建立）：架构每个模块须能指回本表某条需求；推导方法见"需求→架构（架构显著性需求筛法）"一课，验证目标为 `doc/ipad-cfd-teaching/architecture.md`。
