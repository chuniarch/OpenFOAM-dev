# 《怎么写架构决策汇总表》速查卡

> 一页纸方法卡。用于产出「已定决策汇总表」（如 `architecture.md §0`）及其展开的「ADR 台账」（§13）。③架构主用；④详设 / ⑤实现冒出新岔路时同样适用。
> 配套实例：本项目 `architecture.md` §0（汇总表）+ §13（ADR 全文）。

## 总纲（一句话）
**架构决策表 = 把你建造时「被迫分岔、且选错难回头」的路口，逐个记成台账。**

## 一行 = 一个「被迫的选择」（两道关）
某件事要占一行，须**同时**过两关：
1. **真有岔路？** ≥2 个互斥、都走得通的选项。（只有一条路可走 → 不是决策）
2. **影响大 / 难回头？** 牵动多个模块，或定下后改起来痛 / 贵。

两关都过 = 架构岔路口 = 占一行。

## 决策从哪来：三把扫帚（捞候选，宁滥勿缺）
- **A. 需求 / 约束扫（产出最高）**：逐条扫 NFR + 约束，每条问「为满足它，我是不是被迫做了某个技术 / 结构选择？」——**岔路口多半是 NFR / 约束创造的（ASR 筛法）**。
- **B. 系统解剖扫**：套下方「通用槽位清单」，逐槽问「我这个系统在这槽里选了啥」。
- **C. 不可逆性扫**：问「哪些选择以后改起来最贵 / 最痛？」（语言、数据格式、许可…）——必上桌，哪怕当时几乎是随手默认的。

## 流程：捞 → 筛 → 查漏
1. **捞**：三把扫帚各过一遍，列出全部候选。
2. **筛**：每个候选过「两道关」，淘汰不合格的、合并近似的。
3. **查漏（反向自检，最值钱）**：倒过来问——**「每一条 NFR / 约束，在表里都找得到它逼出的那个决策吗？」** 找不到 = 要么漏了决策（补上），要么该需求其实不具架构显著性（也是有价值的结论）。即拿需求清单当**对账单**（第一课「可追溯」的反向用法）。

## 颗粒度准则
**「团队会为它开一次会吵一架吗？」** 会 → 值得占一行；不会（太小如配色 / 太大如「做个 App」）→ 不上。

## 什么**不**进表
- **主观、靠评审收敛的**（配色 / 圆角 / 美感）→ 归设计稿评审（如 NFR6）。
- **只有一条路的**（没得选）。
- **太局部的实现细节**（某函数怎么写）→ 归详设。
- **还没拍板的** → 先进「开放决策点」清单（如 D1–D4），拍板后才进。

## 表 vs ADR 的分工
**汇总表 = 目录**（项 + 一句话压倒性理由）；**ADR = 章节**（背景 → 决策 → **落选选项及被哪条需求否决** → 后果与缓解 → 追溯）。别在目录里写正文，否则表会爆。

## 通用「系统解剖槽位」清单（扫帚 B 的弹药，可复用到 ④⑤）
- 运行环境 / 语言 / runtime
- 数据：模型 · 存储 · 格式 · 驱动方式
- 核心逻辑：自研 vs 复用库
- 呈现：UI 框架 · 图形 · 文本 / 公式 · 动画
- 模块结构：分层 · 依赖方向 · 模块间通信
- 集成边界：外部服务 · 平台规则（商店 / 沙盒）· 网络 / 离线
- 横切关注点：性能 · 安全 · 许可合规 · 可测试性 · 可演进 / 扩展

## 微例（看方法跑起来）
- **「引擎用 Swift 重写」**：扫帚 A（约束 C1∧C2 逼出）+ 扫帚 B（语言槽）+ 扫帚 C（语言不可逆）= 三杀 → 铁定一行。
- **「公式用 SwiftMath」**：扫帚 B（公式呈现槽）摆出岔路；NFR5 离线**砍掉**「WebView / KaTeX」那条腿 → 落子 SwiftMath。
- **反例「按钮配色」**：无互斥技术岔、可随时改、主观 → **不上表**（归 NFR6 设计评审）。
