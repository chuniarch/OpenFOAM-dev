## 2. 教学线：讲解过的关键概念（最有价值，尽量保真）

> 本会话教学占比很大，且经历了「讲太深 → 用户看不懂 → 退回大白话重讲」的反复。以下把讲通了的概念连同**类比**一并保真记录（类比是它们最终讲通的关键）。

### 2.1 三套编号系统（本会话踩过的最大混淆源）

用户中途两次被编号绕晕（"完全看不懂在干什么""太乱了"）。根因：会话里同时存在**三套编号**，我一度复用了同样的圈码：

- `①–⑥` = 软件工程**大阶段 / 过程**：①需求工程 → ②需求分析/建模 → ③架构设计 → ④详细设计 → ⑤实现 → ⑥验证。（现在在 ③，已冻结）
- `③-1 .. ③-5` = 我在 ③ **内部**开的施工清单（见 §0）。**只属于③**。
- `M0–M5` = **产品交付里程碑 / 路线图**（`architecture.md §8`）：M0 引擎内核 → M1 可视化 → M2 源码入门 → M3 探针+字典 → M4 打磨发布 →（发布后）M5 AI 答疑 → 之后 FR6 保存/分享。目前**只有 M0 有代码**。

**教训**：三套不能混用、不能复用圈码。后续阶段（④）如开内部清单，用 `④-1/④-2…`。

另澄清两组常被混淆的关系：
- **需求工程 vs SRS**：不是前后两步，是「活动 vs 产物」。①需求工程这个**阶段**，产出的那份正式文档就叫 **SRS（需求规格 = `requirements.md`）**。
- **大阶段 vs 里程碑**：①–⑥ 是「怎么把事做出来的过程」；M0–M5 是「产品分几批交付的路线图」。两条不同的轴。

### 2.2 架构设计是什么 + 三种产物

架构设计在解一个问题：把②的「需要什么」翻译成「**由哪些大块组成、块怎么连、为什么这么切**」。交付三种产物：

| 产物 | 是什么 | 本项目对应 |
|---|---|---|
| **结构视图** | 分层 / 模块 / 依赖方向 | `§1` 四层图（展示/联动/引擎/资源） |
| **协作视图** | 块之间怎么通信 | `§6` 单一事实源联动；`§15.2` 事件相位序 |
| **ADR** | 每个关键抉择的「背景→选项→决策→后果」 | `§13`、`§15.1` |

关键点：本会话的 ③ **不是白纸作画**，而是「正规化 + 消化新输入 + 补缺口 + 评审冻结」四步收口——v0.2 已有抢跑架构。

③ 的验证方式 = **架构评审**（不是跑测试）：**断言核实**（源码路径/行号/取值对真仓库查证）+ **场景走查**（拿②用例在架构上走一遍）。呼应第一课「可评审 vs 可验收」：架构归「可评审」（专家读了判对错），代码才归「可验收」（跑测试判红绿灯）。

### 2.3 ADR 是什么、为什么

ADR = 架构决策记录。**架构里最贵的不是「选了什么」，而是「为什么没选别的」**。半年后有人问「为什么不直接把 OpenFOAM 编进来」，没有 ADR 就会反复重打这场仗。ADR 把「落选选项 + 被哪条需求否决」钉死，是决策的**不可变历史**（要改决策就新增一条取代，不抹改旧条）。

体例：**背景（指回 SRS）→ 决策 → 落选选项（及否决它的需求）→ 后果与缓解 → 追溯**。落选选项一律写明被哪条 FR/NFR/C 否决，杜绝「事后正当化」。

### 2.4 ASR 筛法（需求 → 架构）

不是每条需求都影响架构。**NFR 与约束通常比 FR 更具「架构显著性」**（ASR = Architecturally Significant Requirement）。本会话一个现场印证：11 条 ADR 的**落选选项几乎全是被 NFR 与约束（C1–C4、NFR1–NFR6）否决的，FR 极少直接否决某个选项**——因为决定架构长相的是质量属性和约束，不是功能清单。

### 2.5 接口 + 关注点分离（本会话的「破冰」概念，靠「报幕/卡拉OK」类比讲通）

这是 `③-3`（引擎事件接口）的软件工程内核。用户一度完全看不懂，退回大白话后讲通：

- **产品目标（"执行游标"）**：仿真一边跑，屏幕一边像**卡拉OK 滚动高亮**——程序现在跑到源码**这一行** → 对应**这个数学项** → 正在改变流场里的**这一块**，代码/公式/结果**三处同时高亮、跟着计算往前滚**。这是「点一处、亮多处」的灵魂。
- **接口（interface）**：引擎和界面是两个模块，它俩「对话」的**约定形状**就叫接口。**定接口正是架构设计的核心活儿之一**。
- **关注点分离**（黄金纪律）：
  - **引擎只管「算 + 报幕」**：吐出一条条「我刚做了什么」的纯数据消息，**完全不碰界面**（不知道有没有高亮、动画）。
  - **界面只管「听 + 画」**：收到消息，自己决定怎么高亮怎么动。
- **为什么死守这条线**：① 引擎能脱开界面**单独测试**；② 以后换界面、换渲染，引擎一行不用改。**改一边不牵动另一边——这就是好架构。**

### 2.6 分层架构深挖（用户问「为什么资源层在最底？基础工具不是该在底吗？」）

这是讲得最透的一节。核心澄清：**「底层」有两种意思，用户套用的是另一种。**

- 这张图的「层」按两件事排：① **离用户的距离**（越上越贴近用户眼睛手指）；② **依赖方向**，且有铁律——**依赖只能向下；下层不知道上层存在。**
- 所以这里的「底层」≠「一堆基础工具」，而是 = **被别人依赖最多、自己谁也不依赖、最稳定的那层**。
- **为什么资源层在底**：它是全 App 的**原料/地基**（案例数据、真实源码片段、映射表，都是惰性内容）。引擎要算得**读**它的案例数据；展示层要显示源码/公式得**读**它的片段和映射；但它**不调用任何人**。「谁都依赖它、它不依赖谁」正是「最底层」的定义。这套排法叫「**展示 → 逻辑 → 数据**」，是 App 架构最常见分层惯例。用户「底层=地基」的直觉没错，只是这里地基是**内容**不是**工具**。
- **「基础工具」去哪了**：用户想的「底层=通用工具」（日志/数学库/系统封装）是**另一种分层风格**（平台/框架式，按通用→专用排）。这张图排的是「这个 App 自己的代码与内容」。真正的基础工具——Foundation、Metal、SwiftMath、iOS 系统——是**外部平台**，垫在四层**全体之下**（图里没画），不算这个 App 的层。
- **「资源层和其他三层是直接上下级吗？」——不是严格一对一**。它是**被多层共享读取的公共地基**：引擎读「案例数据」；展示层**越过**中间两层直接读「源码片段/映射/公式」。这叫「**宽松分层**」（上层可够到不相邻的下层）。它与上三层唯一硬关系就是铁律：**箭头只从上往下指，它自己没有向上的箭头。**
- **餐厅类比**：展示层=前厅服务员（面客），引擎层=后厨（做菜），资源层=**食材仓库**。仓库在「最里/最底」不因它是「工具」，而因它是**一切的原料**：后厨进去拿料做菜（引擎读案例数据），服务员有时也直接进去拿瓶装饮料端给客人（界面直接读源码片段）。仓库不关心谁在炒谁在端，只管被取用。
- **判断分层画对没有，就盯一件事：有没有一根箭头往上指。** 没有，层就立得住。若资源层/引擎层反过来 `import` 界面的东西，就是「**循环依赖**」——分层架构头号大忌。
- 接回本会话早先立的纪律：「**引擎层零 UI 依赖、可单测**」正是这条铁律的现身（下层不知上层存在，故能脱开界面单测）。

### 2.7 数据契约 + 为变化而设计（`③-4` 的软件工程课，用「仓库+填表格式」类比）

- **资源层**：App 离线教学（NFR5），所有素材随 App 打包在里面 = 这个「素材仓库」。
- **数据契约（data contract）**：仓库素材不能乱堆，得有**统一填表格式**；谁写素材都按这张表填、App 按这张表读。这张「格式」就是契约，是「写素材的人」与「读素材的 App」之间的约定。
- 本课的软件工程课 = **为变化而设计**：
  - **开放-封闭原则**：对「加新东西」开放、对「改旧东西」封闭。坐标字段（D4 手工布局）做成**可选**，将来上自动布局时旧数据不失效——新增不破旧。
  - **版本化**：`version:1`，格式变了升版本，新旧平滑兼容（也接 FR6 导出兼容）。
  - **唯一事实源洁癖**：graph 的节点**不重复存源码**，只用 `mappingId` 指回卡片；否则同段代码存两处迟早漂移。

### 2.8 怎么写架构决策汇总表（应用户「我怎么也能写这种表」而生，已存速查卡）

- **总纲**：架构决策表 = 把你建造时「**被迫分岔、且选错难回头**」的路口，逐个记成台账（岔路口台账）。
- **一行 = 一个被迫的选择（两道关）**：① 真有岔路？（≥2 个互斥可行选项，只有一条路不算决策）② 影响大/难回头？（牵动多模块，或定下改起来痛/贵）。两关都过才占一行。
- **决策从哪来（三把扫帚，捞候选宁滥勿缺）**：A. 需求/约束扫（产出最高，逐条 NFR+约束问「逼出什么选择」）；B. 系统解剖扫（套通用槽位清单：语言/runtime、数据、核心逻辑、呈现、模块结构、集成边界、横切关注点）；C. 不可逆性扫（哪些选择改最贵，语言/数据格式/许可必上桌）。
- **流程**：捞 → 筛（过两道关、合并近似）→ **查漏（反向自检，最值钱）**：倒过来问「每条 NFR/约束，在表里都找得到它逼出的决策吗？」找不到 = 漏了决策 或 该需求不具架构显著性。即拿需求清单当**对账单**（可追溯反向用）。
- **颗粒度准则**：「团队会为它开会吵一架吗？」会 → 占一行；不会（太小如配色 / 太大如"做个App"）→ 不上。
- **什么不进表**：主观靠评审收敛的（配色/圆角/美感）；只有一条路的；太局部实现细节；还没拍板的（先进「开放决策点」清单，如 D1–D4）。
- **表 vs ADR 分工**：汇总表 = 目录（项 + 一句话压倒性理由）；ADR = 章节（完整背景/落选/后果）。别在目录写正文。

### 2.9 产品命名（用户问「叫 iCavity 是不是锁死了扩展？」）

- **结论：名字技术上锁不死任何东西，但用户的直觉对——这是个「气味不好」的名字。**
- `iCavity` 是 `# 产品工作名`（working name / 代号），开发期占位、本就预期会换。
- **名字 ≠ 技术**：能不能加新案例跟顶层文件夹叫什么毫无关系；扩展能力住在 **ADR-005（案例=数据、可插拔）** 里。加个 elbow 案例只是 `Resources/Cases/elbow/` + 数据，框架/UI/引擎一行不改。
- **但它是经典命名陷阱**：「拿 MVP/第一个特性命名产品」会把团队脑子锚死、有「用着用着就上架」的惯性、且和愿景（§1「OpenFOAM 引桥课/源码入门」）对不上。**产品名该跟着「不变的价值主张」走，而不是「第一个实例」。** 类比：一家想做整个 OpenFOAM 菜系的馆子，取名「方腔小炒店」，招牌把自己做小了。
- **巧的是真代码已站在用户这边**：M0 引擎包根本不叫 iCavity，叫 **`FoamMini`**（迷你版 OpenFOAM），与案例无关、与愿景对齐。§9 的 `iCavity` 是张过时草稿名。
- 命名属**品牌/NFR6 范畴、可逆、留到后面定**（现在纠结正式名是 bikeshedding）。

### 2.10 M = 里程碑；M0 = FoamMini；spike

用户问「M0 到底在哪？仓库里找不到」。答：
- **M = 里程碑（Milestone）**，`architecture.md §8`。M0 是**计划标签，不是文件夹**；其**产物**是 Swift 包 `ipad-cfd-teaching/FoamMini/`（15 文件）。
- **找不到的真正原因是分支**：这条教学线的所有文件（当年）只在功能分支上，**master 上一个都没有**（当年 `master:0` 文件）。
- **为什么「才到③架构」就有代码**：M0 是一次**提前的概念验证（spike）**——先写个能跑的迷你引擎，验证「Swift 移植真能复现 cavity 流场吗」，给架构吃定心丸，故它跑在正式 ④⑤ 前面。诚实状态：源码已搭建，**本环境无 Swift 工具链、未编译验证**。

## 3. 架构决策记录 ADR-001..011（决策 + 理由，保真）

> 体例统一：决策 / 落选选项（被哪条需求否决）/ 关键后果。全文见 `architecture.md §13、§15.1`。

**ADR-001 · 求解引擎用 Swift 重新实现极简 FVM 内核**
- 决策：Swift 从零实现 Mesh/Field/fvm/fvc/FvMatrix/LinearSolver/PISO，不移植 OpenFOAM 本体二进制。
- 落选：整体交叉编译 OpenFOAM C++ — 被 **C2**（MPI/wmake/动态库在 iOS 不可行）+ **C1** 否决；C++内核+Swift桥接 — 损「好调试好优化」；在线/云端求解 — 被 **NFR5**（运行属静态层须离线）否决。
- 追溯：C1/C2/NFR1/NFR4/NFR5。关联 ADR-003。

**ADR-002 · 源码面板直接展示真实 OpenFOAM C++ 源码**
- 决策：展示真实 `icoFoam.C` 等文本，非手写示意码、非 Swift。
- 落选：自写「等价讲解」伪代码 — 不被否决但削弱权威感，**保留为 GPL 上架前退路**；展示 Swift 引擎码 — 被 **FR4** 否决（要看懂的是 OpenFOAM 的 C++）。
- 后果：触发 **C3**（复制+分发 GPL 文本、与 App Store 冲突，🔴 高）→ 缓解见 ADR-009。追溯：FR4/愿景/C3。

**ADR-003 · Swift 引擎是真实 C++ 的「忠实移植」，靠「函数↔源码映射表」对齐**
- 决策：Swift 顶层与 `icoFoam.C` 近乎逐行对应；资源层映射表 JSON 把每个 Swift 符号绑定到「真实源码行区间+公式+解释」；`fvm.*`返回矩阵、`fvc.*`返回场，**类型系统在编译期强制隐式/显式之分**。
- 落选：自由实现再「凑」源码 — 被 **FR4 可追溯性**否决（否则即「骗」）；不建映射表靠命名约定 — 被「可验收」（T7 须逐条核验）否决。
- 后果：移植须持续校准（`Fvc.div` 缺口、`adjustPhi`/`setReference` 一致性）。追溯：FR4/FR5。

**ADR-004 · 首个案例锁定 icoFoam + 2D cavity**
- 决策：MVP 唯一案例 = icoFoam 解 2D cavity；4 种 BC；20×20 均匀网格；锚点 `tutorials/legacy/incompressible/icoFoam/cavity/cavity/`。
- 落选：多求解器/多案例首发 — 被 **§6+NFR2** 否决；3D/湍流/复杂网格 — 被 **§6 明确不做** 否决。追溯：FR1/NFR2/C4/§6。

**ADR-005 · 案例数据驱动、可插拔（案例 = 结构化数据 + solver 标识）**
- 决策：`CaseData`（control/schemes/solution/properties/mesh/fields + solver 标识），引擎数据驱动。
- 落选：每案例硬编码 Swift — 被 **§6 演进策略**否决为长期形态；解析真实字典全语法 — 被 **NFR2/简化纪律**否决。追溯：§6/FR2/C1。

**ADR-006 · 数学公式用 SwiftMath（原生、离线）**
- 决策：SwiftMath 渲染数学模式 LaTeX 子集，`latex`字段 → `MTMathView`。
- 落选：WKWebView+KaTeX — MVP 被 **NFR5（离线）+NFR4（WebView 开销）**否决（保留为复杂排版局部升级位）；预渲染图片 — 被可维护性否决。追溯：FR4/NFR4/NFR5/NFR6。

**ADR-007 · 结果可视化用 Metal / SwiftUI Canvas**
- 决策：Metal（场/云图/流线 GPU 渲染）+ Canvas（残差曲线轻量绘制），按负载分工。
- 落选：整搬 ParaView/VTK — 被 **NFR6（避经典 CAE 观感）+NFR1** 否决；纯 SwiftUI 无 Metal — 场刷新流畅度被 **NFR4** 推向 Metal。追溯：FR3/NFR3/NFR4/NFR6。

**ADR-008 · 四层架构 + 联动层「单一事实源」**
- 决策：展示 / 联动（`@Observable` 持 `highlightedNodeID + iterationState + probedCell`）/ 引擎（纯计算零UI）/ 资源；依赖**自上而下单向**。
- 落选：各面板各自持状态互调 — 被「一致性」否决（多份状态必漂移）；引擎直接驱动 UI — 被 **ADR-001（零UI/可单测）**否决。追溯：FR4/FR5/NFR4。

**ADR-009 · GPL 策略：原型期内嵌、上架前切「外链 + 自写等价讲解」**
- 决策：原型期先内嵌真实源码不为合规分心；**上架前**改造为 ①源码外链 openfoam.org + ②自写等价讲解，并确认整 App 分发许可。
- 落选（见 §11.3 五选项）：纯内嵌上架 — 被 **C3** 否决；放弃 App Store 走自签 — 被商业化目标否决（留作退路）。追溯：C3/ADR-002。

**ADR-010 · 图形化编辑：表单 ↔ dict 文本 双向同步**
- 决策：图形控件（滑杆/选择器/步进器）+ 同显等价 dict 文本，双向同步，作用于 `CaseData`。
- 落选：纯文本编辑 dict — 被 **NFR3**（触屏手敲差）否决；纯表单不显 dict — 被 **FR2**（须可见等价 dict，本身是教学法）否决。追溯：NFR3/C1/FR2。

**ADR-011 · 引擎↔联动层事件接口 = 同步可恢复「求解游标」+ 事件枚举（AsyncStream 作播放适配）**（详见 §5 / `architecture.md §15`）
- 决策：引入同步、确定性、可恢复的 `SolveCursor`（`advance()->SolveEvent`）；`SolveEvent` 纯值类型零 UI；联动层在其上包 `AsyncStream`（播放）+ `advance()`（单步）；老 `step()/run()` 降为便利包装。
- 落选：纯同步回调 `step(emit:)` — 无法子步暂停/恢复，被 **D2 子步单步+UC4** 否决；纯 AsyncStream（引擎内开 Task 异步） — 损 **ADR-001 可单测 + T5 逐位一致**（异步非确定），故 AsyncStream 只在联动层用不下沉引擎；维持现状（仅时间步粒度） — 被 **FR4/FR5/UC6-E2** 否决。追溯：FR4/FR5/NFR4/D2/UC6-E2/T5。

> 台账观察：ADR-001..003 是「源码入门」差异化三连扣（Swift 跑 + 真 C++ 看 + 映射表锁一致）；004/005 锚定范围与可演进性；006/007 呈现层选型；008 结构骨架；009 GPL；010 编辑范式；011 引擎事件接口。落选选项几乎全由 NFR/约束否决——ASR 筛法现场印证。

## 5. 引擎↔联动层事件接口（§15，`③-3` 的详细产出）

**缺口（§1.1 复述并经代码核实）**：现有引擎 `IcoFoam.step()` 是一条直线跑完整个时间步、中途无事件无暂停点；`run(endTime:onStep:)` 每时间步才回调一次 `StepReport`——**每时间步一次，粗粒度**。而 FR4「点算子→高亮真实源码行」、UC6-E2「运行时执行游标脉冲」、D2/UC4「子步单步」都要**算子/子步级**广播。

**决策（ADR-011）**：见 §3。核心是**同步可恢复「求解游标」`SolveCursor`**：`advance()->SolveEvent` 执行下一相位、就地更新场、返回事件。为什么不是纯 AsyncStream：单步一致性（T5）+ 可单测（ADR-001）要**确定性**，异步调度引入非确定；故并发只在联动层、引擎保持同步。

**SolveEvent 相位序（对照真实 icoFoam.C，行号已核实）**——每相位带 `nodeID`（=②思维导图节点 id），联动层据此同时点亮：思维导图节点脉冲 + 源码行 + 公式 + 结果面板。这就是「协作视图」的算子级落地：

| 0 | timeStepBegin | 67–69 | icoFoam |
| 1 | op(.ddt,.lhs) | 77 | fvm.ddt |
| 2 | op(.div,.lhs) | 78 | fvm.div |
| 3 | op(.laplacian,.lhs) | 79 | fvm.laplacian |
| 4 | assembleMomentum | 75–80 | icoFoam.UEqn |
| 5 | op(.grad,.rhs) | 84 | fvc.grad(p) |
| 6 | solveMomentum | 82–85 | icoFoam.UEqn |
| 7 | pisoCorrectorBegin(c) | 88–91 | icoFoam.piso |

| 9 | assemblePressure(c) | 109–112 | icoFoam.pEqn |

**两档单步语义（D2）**：时间步单步 = advance 至下一 `timeStepEnd`；PISO 子步单步 = advance 一个相位即停。

**T5 逐位一致不变量（关键，留给④守门）**：游标按相位推进 n 步的场，必须与连续 `run` 跑 n 步**逐位一致**——因为游标只是把同一套 `step()` 算术**重新切相位、不改运算与顺序**。这给 M0 引擎压了一条**「重构须行为保持」**债。

**诚实边界**：M0 现有数值简化省了真实 icoFoam.C 三行——`fvc::ddtCorr`(L96)、`adjustPhi`(L99)、`constrainPressure`(L102)——这些行**源码面板照常显示**（ADR-002），标「展示未执行」状态，待 M0 补齐再接相位。类型草案（`SolveEvent` 枚举 + `SolveCursor` 类）见 `architecture.md §15.3`，均纯 Swift、零 UI。

## 6. 资源层契约升级（§16，`③-4`）

`§5` 原定资源层只放 `mappings`（符号→源码行/公式/解释，一堆「卡片」）。②（`analysis-model §2.4/§3`）新增 `Relationship`（思维导图的「边」）——卡片间需要「连线」。故契约由 `mappings` 升为 **`mappings + graph{nodes, edges}`**，并为 FR7（M5）预留 `contextPackHook`。

顶层形状（`version:1`；node 带 `mappingId` 指回卡片 + 可选 `x/y`；edge 带 `type/arrow/label`，枚举沿用 `analysis-model §3.2`）。三条纪律：① 节点不重复存源码、只 `mappingId` 指回（唯一事实源）；② 坐标可选（D4，开放-封闭不破旧）；③ `ContextPack` 只留挂点不现在实现（= 某 mappingId 卡片内容 +（可选）当前 SolveEvent/状态，M5 才装配，故是「加规则」非「改格式」）。构建期 lint 沿用 `analysis-model §3.3`（edge 两端存在、枚举合法、非 concept 节点源码行真实存在=T7、无孤儿节点）。

追溯链（干净实例）：需求 §9（思维导图候选概念）→ ② 领域模型新增 `Relationship` → ③ 资源层 `graph.edges` → ⑥ 验收 T7。

## 7. 阶段末评审与冻结（§17，`③-5`）

**场景走查（②用例 + 质量场景 → 架构接得住吗）**：
- **UC6 读源码 + UC4 单步**（FR4/FR5）：`SolveCursor.advance()`→`SolveEvent(nodeID)`→联动层 `highlightedNodeID`→思维导图节点+源码行+公式+结果同时点亮。✅ 全链路有模块接住。

- **NFR5 离线降级**：飞行模式静态层（引擎+资源+可视化）全在端上可用；AI 入口置灰。✅（分层 ADR-008 兑现）
- **NFR4 性能**：20×20 网格 + Metal + Canvas；单步走游标一相位。✅

> 走查产出 **1 个 ④ 待办（UC5 矩阵行只读访问器），0 个③阻塞项**。这也是场景走查的价值示范：**纸上走一遍就把这种洞提前抓出来**，不用等写代码写到一半才发现。

**断言核实**：本会话复核 `icoFoam.C` 关键行号（UEqn 75–80、动量预测 82–85、PISO 88–127、fvm.ddt/div/laplacian 77/78/79、fvc::grad(p) 84、adjustPhi 99、constrainPressure 102、pEqn 109–112、setReference 114、通量/速度修正 120/126）全部命中；cavity 锚点路径、§2 类映射 12 条源码路径、§4 案例取值延续 §2.1/§4.5 既有核实。**诚实边界**：§15 的 `SolveCursor`/`SolveEvent`、§16 的 graph/contextPackHook 是**设计契约，尚无对应 Swift 代码**（M0 仅 `step()/run()`）；落地=④详设+⑤实现，背 ADR-011「重构须逐位一致」债。架构层断言（路径/行号/取值）为真；实现层断言留给下游验收。

**冻结声明**：§13（ADR-001..011）+ §14（D1–D4）+ §15 + §16，经走查与断言核实，**③架构设计冻结为 v0.3**。遗留：1 个④待办、D1 暂定项（待④ UI 评审复核）、§15/§16 实现债（④⑤ 落地）——均登记不阻塞。
