## 0. 给接手模型的关键指示（务必先读）

1. **用户身份**：需求方 + 学习者（自述软件工程「几乎全忘了」）。每一步**先讲该阶段理论**（这步叫什么、产物是什么、为什么在这个位置），**再实操**。
2. **★教学高度——本线最大教训★**：用户**不是工程师**。每次**先用大白话 + 类比**讲清「在干什么、为什么」，**工程图纸（代码 / 表格 / JSON）落进文档**，对话里只给**概念**，必要时配**一小段带注释的示例**即可。**严禁工程师对工程师式地堆术语和代码表**——③阶段曾因此被用户多次叫停（"完全看不懂在干什么""太乱了"）。**判据：用户能用自己的话复述"在干嘛"，才算讲到位。**
3. **★全文呈现纪律★**：重要内容**必须完整写在对话里**，不能只改文件后给摘要；引用任何文档章节（如「§15」）前，**先把该章节全文贴出来**。用户多次因「只改文件不贴正文」而叫停。
4. **★编号别再撞号★**：已有**三套编号**，绝不能混用或复用同样的圈码：
   - `①–⑥` = 软件工程**大阶段 / 过程**（现在到 ④）；
   - `M0–M5` = **产品交付里程碑 / 路线图**（`architecture.md §8`，目前只有 M0 有代码）；
   - 各阶段**内部**可能再开的施工清单。
   ③阶段曾因内部清单复用 `①②③④` 与大阶段撞号，把用户绕晕。④如要开内部清单，**用 `④-1 / ④-2 …` 或字母**，并一开始就申明「这只属于 ④」。
5. **协作风格**：理论先行；用本项目真实材料做实例；**关键选型交用户拍板（用 `AskUserQuestion`）**；每次产出**落盘 + 全文呈现 + commit/push**。push 用 `git push -u origin <本会话被指派的开发分支>`；**若该分支不是 `awesome-einstein`，先把 `awesome-einstein` 合并进来再开工**（③就是这么把 `modest-clarke` 的成果接过来的）。
6. **不跳步、不颠倒**：可回头改上游（已发生 requirements v1.1–v1.3、architecture v0.2→v0.3 的回流），但不得在未对齐上游的情况下锁死下游。

## 1. 教学线已走到哪（保持连贯）

- **大阶段地图**：①需求工程 ✅ → ②需求分析/建模 ✅ → ③架构设计 ✅（刚冻结 v0.3）→ **④详细设计（本阶段）** → ⑤实现 → ⑥验证。
- **已教概念清单（④可直接援引，不必重讲）**：可追溯（向前=需求→验收 / 向后=模块→需求）；可验收 vs 可评审；需求→架构 ASR 筛法（NFR/约束最具架构显著性）；用例=SRS 动词投影 / 领域=名词投影；ADR（背景→选项→决策→后果）；架构决策表写法（见速查卡）；分层架构（**依赖只向下、下层不知上层、单一事实源**）；关注点分离（引擎只「算+报幕」、UI 只「听+画」）；为变化而设计（开放-封闭、版本化）。
- **④是什么（一句话）**：③说清了「由哪些大块组成、怎么连、为什么」；**④钻进每个大块，把它的内部设计到「可直接写代码」的程度**——具体类型、函数签名、算法、数据结构、代码级接口契约、关键时序。
- **④大概率要教的新概念**：接口契约精化（从草图 API → 可编译签名）、**行为保持的重构 refactoring**（接 T5 逐位一致）、数据结构与算法选型、契约式设计（前置/后置条件）、**可测试性设计**。

## 4. ④ 的验证方式

- **评审（同③）**：**断言核实**（引用真实代码/行号去查证）+ **场景走查**（拿②用例在详设上走通，每步落到具体函数/类型）。
- **★④特有：可编译性 / 可测试性自检★** —— 详设的接口签名应「能在脑子里编译过」，关键算法应能**写出单元测试判据**。注意：**本环境无 Swift 工具链，代码不能真编译**；故 ④ 产出是「设计 + 测试判据」，真编译/真跑留 ⑤。
- **T5 守门**：任何对引擎的重构，必须保证「单步 n 次 == 连跑 n 步**逐位一致**」。
